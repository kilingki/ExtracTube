### 1. 실행 범위와 완료 조건

**Cursor는 1단계에서 탐색용 4개 영상으로 13개 설정을 각각 2회씩 총 26회 순차 실행한다. 이후 탐색 결과만으로 잠정 후보 1개를 확정하고, 2단계에서 E00 대조군과 후보를 각각 2회씩 8개 전체 영상으로 총 4회 새로 실행한다. 합계 30개 실행 슬롯이다. 첫 회차나 탐색 단계가 끝났다는 이유로 종료하지 않고, 최종 확인과 통합 보고서 작성까지 자동 진행한다.**

- 1회 실행은 해당 단계의 고정 입력 전체에 대한 boundary → conflict → verify → units 처리다. 탐색은 4개·1435문장, 최종 확인은 8개·3355문장이다. 지정한 입력 일부만 성공한 결과는 완료로 세지 않는다.
- 병렬 모델 호출·병렬 실험은 사용하지 않는다. 한 실행 안에서도 기존처럼 영상·단계를 순차 처리한다.
- 같은 설정의 반복은 새로운 모델 호출로 수행한다. 결과 캐시·T1 응답 재사용으로 반복 횟수를 채우지 않는다. 저장 응답 재생은 별도의 무결성 검사로만 사용한다.
- 탐색 순서는 search/r01에서 E00→E12, 이어서 search/r02에서 E00→E12다. 후보 확정 후 confirm/r01에서 E00→selected, 이어서 confirm/r02에서 E00→selected로 실행한다. selected는 확정한 기존 E01~E12 중 하나이며 새 조합 설정이 아니다. 최종 확인에서도 모델을 새로 호출하고 탐색 결과를 재사용하지 않는다.
- 사람이 중간 검수에 응답하지 않아도 다음 사전 정의 실험은 계속한다. 미검수 상태는 보고서에 남긴다. 품질 수치가 나쁘다는 이유만으로 후속 회차를 취소하지 않는다.
- 정상 완료는 탐색 26개와 최종 확인 4개, 총 30개 슬롯 각각이 validated 또는 명시적인 failed/skipped 상태이고, 통합 보고서와 재개 가능한 상태 파일이 생성된 경우다. failed/skipped가 있으면 “30회 성공”이라고 쓰지 않는다. 후보가 없으면 최종 후보 슬롯 2개는 skipped/no_eligible_candidate로 기록하되 최종 E00 슬롯은 실행한다.
- 무한 탐색은 하지 않는다. 재시도는 아래 한도 내에서만 하며, 이 표 외의 새 설정을 자율 추가하지 않는다. 사용자 중지 또는 누적 실행 시간 48시간에 도달하면 저장 후 중단하고 남은 슬롯을 pending으로 남긴다. T1 호출 시간 기준 탐색 4개는 회당 약 15분, 전체 8개는 약 32분이다. 26×약15분 + 4×약32분은 대략 8.5~8.6시간으로, 종전 약 14시간보다 줄어든다. 사전 점검·실패 재시도·사고 모드·설정별 호출량·평가 시간에 따라 실제 시간은 달라진다.

- ASR·문장 분할·metadata를 재생성하지 않는다. 문장 index·원문·시각·source_chunk_index를 유지한다.
- INFER_BASE_URL=`http://127.0.0.1:8095`, INFER_MODEL_ID=`qwen-vlm`, BODY_MODEL=`qwen3.8-27b`를 전 회차에서 유지한다. 실행 환경의 localhost가 실제 서버인지 확인한다. 다른 모델로 자동 대체하지 않는다.
- 실제 모델 체크포인트·리비전·양자화·서빙 엔진 버전·채팅 템플릿·컨텍스트 상한·서버 생성 기본값을 가능한 범위에서 manifest에 기록한다. 확인 불가 항목은 unknown이다. 응답의 model 문자열만으로 동일 가중치를 보장한다고 쓰지 않는다.
- top_p, top_k, min_p, presence_penalty, repetition_penalty, seed는 기존처럼 요청에서 생략한다. null이나 임의의 새 기본값을 보내지 않는다. 서버에서 적용되는 값을 확인 가능하면 기록하고 campaign 도중 변경하지 않는다. 모델 샘플링 seed와 아래 검수 표본 seed는 별개다.
- 경계·충돌·검증 JSON 응답 계약과 파싱 검증, 실패한 요청의 동일 본문 재시도 최대 2회(첫 시도 포함), 문장 단위 청크 생성, 경계 처리 순서와 keep/merge 알고리즘은 유지한다.
- 최소 검증 문맥은 양쪽 각각 1문장, 글자 예산 초과 시 기존처럼 경계에서 먼 문장부터 제거하고 동률이면 오른쪽부터 제거한다. 최소 문맥도 예산을 넘으면 실패로 기록한다.
- 검수 표본 seed=`20261017`, 단계별 반복 횟수=`2`, 동시 실행 수=`1`, 슬롯 전체 재실행 횟수=`최대 1회`, campaign 시간 한도=`172800초`를 고정한다. 각 단계와 슬롯의 input_ids 및 예상 문장 수를 effective_config.json에 명시한다.

#### 거리별 CONFLICT 렌더링 규칙

원문 CONFLICT의 `문장 index 차이가 1 또는 2인 후보가 연결되어 있다.` 구절이 정확히 한 번 존재하는지 검사한다. 다음 구절로 한 번만 치환하고 나머지 텍스트·자리표시자·JSON 계약은 그대로 유지한다.

| ID | NEAR_DISTANCE | 해당 구절의 실제 텍스트 |
| --- | ---: | --- |
| C1 | 1 | 문장 index 차이가 1인 후보가 연결되어 있다. |
| C2 | 2 | 문장 index 차이가 1 또는 2인 후보가 연결되어 있다. |
| C3 | 3 | 문장 index 차이가 1, 2 또는 3인 후보가 연결되어 있다. |

C2의 전체 문자열은 T1과 바이트 기준으로 동일해야 한다. E07/E08은 후보 군집 거리와 모델에게 설명하는 거리를 함께 맞춘 정책 비교이며, 프롬프트 문자열은 전부 고정한 순수 숫자 비교라고 주장하지 않는다. 거리 변경으로 실제 충돌 후보 집합도 달라질 수 있다. 실행 전 C1/C2/C3와 거리 값의 매핑을 검사한다.

### 5. P1 VERIFY 전문

P0 및 BOUNDARY·C2 CONFLICT는 T1 원문과 SHA-256 일치를 확인한다. C1/C3는 다음 규칙으로 생성하고 실제 렌더링된 프롬프트의 해시를 별도로 기록한다. P1에는 아래 텍스트를 그대로 쓰고, 자리표시자는 기존 render 방식으로 치환한다.

```text
아래 두 구간은 경계 하나로 나뉜 인접 의미 단위의 전체 또는 경계 주변 발췌다. 경계 뒤의 첫 문장이 새로운 주제, 작업 대상, 작업 목적을 시작하면 keep, 같은 대상과 목적에 대한 설명·근거·예시·보충이 이어지면 merge다.

판단 기준:
- 영상 전체의 주제나 상위 작업이 같다는 사실만으로 merge하지 않는다. 예를 들어 같은 상품 등록 과정이어도 상품 상세 설명·상세페이지 등록에서 제조사·인증 정보 입력으로, 또는 상품 기본정보 입력에서 검색 태그 수집으로 넘어가면 독립된 작업 대상과 목적의 전환이므로 keep한다.
- 단순한 클릭, 스크롤, 다음 문장이라는 이유만으로 keep하지 않는다. 같은 필드의 값을 입력하고 저장하는 동작, 같은 키워드를 수집하고 불필요한 항목을 정리하는 동작은 대상과 목적이 계속 같으면 merge한다.
- 앞 설명의 이유·예시가 뒤에 나온다는 이유만으로 새 단위를 만들지 않는다. 반대로 앞 문제에 대한 후속 설명이라는 이유만으로 서로 다른 실행 전략을 합치지 않는다. 사업자 수 확대와 상품 객단가 개선처럼 실행 대상·목적이 달라지면 keep한다.
- 문장 수, 구간 길이, 청크 시작·끝은 경계의 근거가 아니다. 발췌 문맥일 수 있으므로 보이지 않는 내용을 추측하지 않는다.
- reason에는 경계 직전과 직후의 구체적인 대상·목적이 무엇이며 어떻게 달라지거나 유지되는지 한 문장으로 쓴다. '같은 과정이라서' 같은 상위 주제만으로 판단하지 않는다.

JSON 객체만 출력한다.
{"action":"keep","reason":"경계 앞뒤의 구체적인 대상·목적이 어떻게 바뀌거나 이어지는지 한 문장"}
action은 keep 또는 merge다. reason은 비어 있지 않은 문자열이다.

경계 앞:
{왼쪽 문장 줄}

경계 뒤:
{오른쪽 문장 줄}
```

이 예시는 기존 T1 문제를 반영한 개발용 예시다. 같은 영상에서 좋아져도 미관측 데이터에 대한 일반화 개선으로 주장하지 않는다. campaign 도중 예시·프롬프트를 추가 편집하지 않는다.

### 6. 공통 엔진 구현·검사

- 기존 MAX_SENTENCES를 청크와 검증 예산으로 분리한다. E03의 청크 80이 verify 전체 문맥 한도까지 80으로 바꾸지 않도록 한다.
- choose_context는 전체 구간이 VERIFY_FULL_MAX_SENTENCES 및 글자 예산을 모두 만족하면 full로 반환한다. 아니면 양쪽 최대 window만 발췌하고, 총 문장·글자 예산을 넘으면 기존 거리·동률 규칙으로 제거한다. 양쪽 최소 1문장은 보존한다. kind는 실제 window 값에 맞춰 window12/window24로 기록한다.
- request_body에 stage별 max_tokens가 정확히 적용되도록 한다. request_stage의 동일 본문 재시도 계약은 유지한다. 사고 응답의 reasoning_content는 가능한 경우 별도 기록하고, JSON 파싱 대상은 기존 최종 content다.
- 기존 7개 --check를 보존하고, 설정별 경계 조건·예산 분리·문맥 자르기·단계별 상한·설정 누출·중단 재개를 검사한다. 잘못된 구조 검사를 삭제하지 않는다.
- E00 설정으로 저장된 T1의 581건 응답을 네트워크 없이 재생한다. timeout과 출력 경로·추가 manifest 키 등 의도한 메타데이터 차이는 분리하고, 요청 본문의 의미·chunks·proposals·candidates·conflicts·검증 문맥·최종 경계·units·원문·시각이 기존과 일치해야 한다. 이 검사가 통과하기 전에는 모델 실험을 시작하지 않는다.
- 실험 계획의 실효 설정을 비교해 표에 선언된 차이 외의 값이 변하지 않았는지 자동 검사한다. 공유 설정을 mutable 전역값으로 덮어쓰지 않는다.
- --check는 실제 LLM을 호출하지 않는다. --run-all에서 서버 점검·입력 해시 검증 후 전체 순차 반복을 시작한다.

### 7. 자동 반복·실패·재개 동작

사용자가 Cursor에 이 문서를 실행하라고 시키면 아래까지 구현하고 실제 전체 실행을 시작한다. 이 문서는 현재 채팅에서 실험 실행을 요청하는 것은 아니며, 실행 주체는 이후 지시받은 Cursor다.

```bash
python3 -B tests/T1_sweep/run_sweep.py --check
python3 -B tests/T1_sweep/run_sweep.py --run-all
# 중단되었다면 실제 campaign 경로로 재개
python3 -B tests/T1_sweep/run_sweep.py --resume tests/T1_sweep/campaigns/<campaign_id>
```

#### 사전 점검 시점과 집계

- **모든 슬롯의 매 attempt 시작마다** 입력 해시·서버 상태 확인 후, 영상 본 처리 전에 LLM 사전 점검을 1회 수행한다. campaign에 한 번만 수행하는 방식이 아니다. attempt02에서도 다시 수행한다. --check와 단순 연결 확인은 LLM 사전 점검으로 세지 않는다.
- 대상은 해당 단계 input_ids의 첫 영상에서 해당 설정으로 만든 첫 번째 2문장 이상 청크다. search는 Fw-8hZhnH3Q, confirm은 7EJ-xotXiSE가 대상이며, 청크 최대 문장·글자·중첩·BOUNDARY·temperature·thinking·boundary 출력 상한은 해당 실험의 값을 사용한다.
- 동일 요청 최대 2회(첫 시도 포함)라는 재시도 규칙을 적용한다. 모든 시도를 run.json의 preflight.calls 배열에 저장하고, 최종 verdict와 선택된 call_id를 남긴다. 실패하더라도 raw 응답·오류·소요 시간·토큰을 보존한다. T1 원본의 preflight.call 구조를 수정할 필요는 없다.
- 사전 점검 성공 결과는 본 처리 청크 결과로 재사용하지 않는다. 정상이라면 같은 첫 청크도 본 처리에서 새로 호출한다. 사전 점검이 실패하면 해당 attempt의 영상 본 처리를 시작하지 않고 동일한 슬롯 실패 정책을 적용한다.
- 무재시도·무미지원·무실패인 30개 슬롯에는 별도의 사전 점검 호출이 30건 추가된다. 재시도·새 attempt·미지원 판별에 실제 LLM 요청을 썼으면 실제 건수는 달라진다. 완료 슬롯을 resume으로 건너뛸 때는 사전 점검도 다시 호출하지 않는다.
- processing_calls는 각 semantic_units.json.calls의 길이 합, preflight_calls는 각 attempt의 preflight.calls 길이 합이다. total_llm_calls는 processing_calls + preflight_calls + 별도 LLM 지원 탐지 호출 수이며, 범주를 중복 집계하지 않는다. 지원 탐지를 사전 점검 응답으로 판단했다면 별도 호출 수는 0이다. 실패한 attempt 비용도 campaign 전체 합계에 포함한다.

실행기 동작은 다음과 같다.

```text

for repeat in [r01, r02]:
```

- 슬롯 상태는 pending/running/validating/validated/failed/skipped를 구분한다. 프로세스 exit code 0만으로 validated 처리하지 않는다.
- 정상 결과는 해당 슬롯의 지정 입력 전체(search 4개 또는 confirm 8개)가 모두 ok, 입력·문장 보존 검사 통과, 설정 일치, 호출 로그·review·index·저장 응답 재생 검증 통과를 뜻한다. 의미 품질이 좋다는 뜻은 아니다.
- 요청당 최대 2회 실패 후, 원인이 일시적 네트워크·서버 5xx·timeout이면 슬롯 전체를 동일 설정으로 1회만 새 attempt에서 재실행한다. 재실행 대기 30초, attempt02가 최종 한도다. 기존 실패 출력은 남긴다. 최종 성공 attempt만 집계하되 실패 비용은 따로 보고한다.
- JSON 계약·출력 잘림·지원하지 않는 설정·구조 실패는 임의로 프롬프트/토큰/온도를 바꿔 구조하지 않는다. 해당 슬롯을 failed로 기록하고 다음 독립 실험으로 진행한다. 비교 기준 슬롯이 실패해도 다른 슬롯 실행은 계속하며 해당 비교만 unavailable로 적는다.
- 원인이 코드 버그이면 모델 호출을 멈추고 수정·검사한다. 수정 후 코드 해시가 달라지므로 기존 campaign의 엔진을 바꿔 이어가지 않는다. 기존 실행을 partial로 보존하고 수정 버전은 새 campaign으로 다시 시작한다. 모든 슬롯이 같은 엔진 해시를 쓰도록 한다.
- 서버 전체가 반복해서 접근 불가능한 경우 연결 확인을 30초 간격 최대 3회 수행한 후 저장하고 중단한다. 입력 해시 변경·모델/서버 정체성 변경을 감지해도 전체 중단한다. unknown 항목 때문에 중단하지는 않지만 통제 한계를 기록한다.
- --resume은 단계(search/confirm)·실험·반복 번호로 슬롯을 식별한다. selection.json이 있으면 후보와 설정 해시를 확인하고 다시 선정하지 않는다. 후보 선정 전 끊겼으면 남은 search 슬롯부터 재개하고, 26개 search 슬롯이 모두 validated/failed/skipped인 뒤 선정하여 confirm으로 진행한다. manifest와 현재 입력·계획·코드·프롬프트의 해시가 같아야 한다. validated 슬롯은 다시 호출하지 않는다. running/validating 상태로 끊긴 슬롯은 파일이 완전하고 재생 검증이 되면 완료 처리하고, 아니면 incomplete attempt를 남긴 뒤 허용된 다음 attempt에서 재실행한다. attempt 한도 초과 슬롯은 failed다.
- state.json은 임시 파일 저장 후 rename으로 교체하고, 실행 중 로그를 파일로 계속 flush한다. 사용자가 재개하면 터미널 로그를 보고 처음부터 수동 재실행할 필요가 없어야 한다. 셸 세션 종료 후에도 계속해야 하는 환경이면 플랫폼 지침에 맞는 관리 가능한 백그라운드 프로세스를 쓰고 PID·로그·재개 명령을 남긴다.
- 시간 한도는 재개 전 실행 시간을 포함하며, 한도 도달 시 새 슬롯을 시작하지 않고 실행 중 프로세스는 로그·실패 산출물을 보존해 종료한다. 자동으로 시간 한도를 늘리지 않는다.

### 8. 회차별·통합 평가

탐색 회차는 T1 중 동일한 4개 영상 및 표에 명시된 search 기준의 같은 반복 번호와 대조한다. 최종 후보 회차는 같은 confirm 반복 번호의 E00과 비교한다. search/confirm의 총합을 입력 크기 차이를 무시하고 직접 비교하지 않는다. 기준 회차 실패 시 다른 반복을 몰래 대체하지 말고 unavailable로 표시한다. r01 종료 후에도 r02를 진행한다.

metrics.csv에 phase(search/confirm), input_group(search/final_only/all), experiment_id, repeat, attempt, status, config_hash, engine_hash, prompt_hash, model_identity, input_ids, 예상·실제 문장 수, 입력 해시 집합을 포함하고 다음을 영상별·전체로 남긴다.

- 초기 후보 수·충돌 후 경계 수·최종 단위 수·keep/merge 수 및 merge 비율.
- 최종 단위의 문장 수 및 길이(초)의 중앙값·p95·최댓값, 1문장 단위 수, 40문장 초과 단위 수. p95는 정렬한 n개 값의 ceil(0.95*n)번째 값으로 전 회차에서 통일한다.
- 전체/발췌 검증 문맥 건수·문장 수·토큰 수, 청크 수·실제 중첩량·글자 예산 때문에 잘린 청크 수.
- 단계별 호출 수·오류·재시도·finish_reason·입출력 토큰·reasoning 토큰(없으면 unknown), 요청 시간 합계 및 전체 경과 시간. 토큰 정보를 누락한 응답은 0으로 가정하지 않는다.
- 새로 추가/제거된 최종 경계 index 전체 목록과 초기·충돌 단계의 차이. 상류 결과가 다르면 VERIFY만의 효과라고 단정하지 않는다.
- 반복 r01/r02 사이 영상별 최종 경계 집합의 Jaccard와 경계 대칭차 개수. 둘 다 빈 집합일 때 Jaccard=1로 정의한다. temperature=0이어도 완전 재현된다고 가정하지 않는다.
- monotonic/perf_counter 경과 시간과 UTC 시각 차이를 따로 표시한다. T1 시간의 약 112.69초 차이를 혼용하지 않는다.

summary.md는 두 단계의 전체 진행표, 실험별 2회 관측값과 범위·평균, 비교 기준 대비 차이, 후보 선정 근거, 실패·미지원·미검수 목록, 비용·시간을 포함한다. confirm 결과는 탐색 4개·추가 확인 4개·전체 8개를 반드시 구분한다. 장편 Cvu 결과와 과분할 회귀를 별도 요약한다. 2회 반복으로 통계적 유의성이나 일반화를 주장하지 않는다. 사전 점검·실패 attempt 비용은 본 처리 비용과 구분하고 campaign 총비용에는 포함한다.

### 9. 의미 품질 검수와 최종 선택

사람의 정답이 없는 상태에서 실행기가 정답 F1이나 “최적 설정”을 만들어내면 안 된다. 자동 검증과 반복 실행은 사람 검수 완료 여부와 무관하게 끝까지 진행한다.

- 탐색 고정 검수 위치는 Fw-8hZhnH3Q의 102/112, iEMuJiVY9Oc의 264/278이다. H2의 근거·예시 연결과 hGV의 짧은 문답도 검수해 Fw/iEM 개선만으로 후보를 고르지 않는다. CvuE-jyg-N8의 549/560은 최종 확인에서 검토하는 불확실한 후보이며 정답 경계로 강제하지 않는다. 단위 번호가 아니라 sentence_index로 추적한다.
- 고정 검수 표본은 아래 SHA-256 순위 알고리즘으로 영상별 최대 5개를 선정한다. 탐색 4개는 search에서 확정한 동일 목록을 confirm까지 유지하고, final_only 4개는 confirm E00 r01에서 처음 선정한다. 새로 추가·제거된 경계의 합집합도 모두 review_queue.json에 넣고, 양쪽 문맥·회차별 action/reason·출처를 제공한다. 경계 추가뿐 아니라 과분할 증가도 확인한다.
- Cursor가 전사를 읽고 평가하면 reviewer_type=agent, 사용한 모델·평가 기준·근거 문장을 기록한다. 이를 human gold로 표시하지 않는다. 사람이 검수하지 않은 곳은 pending_human으로 남긴다. 사람이 답하지 않아도 다음 실험은 실행한다.
- 단위 수 증가·merge 비율 감소·긴 단위 감소 자체는 품질 점수가 아니다. 서로 다른 작업 대상·목적을 분리하면서 같은 대상의 설명·근거·예시를 유지하는지를 검토한다.
- 사람의 확정 라벨이 있으면 같은 라벨 범위에서 exact boundary precision/recall/F1과 ±1문장 허용 일대일 매칭 F1을 별도로 계산한다. 정의되지 않은 분모는 N/A로 적는다. 일부 경계만 검수한 경우 전체 영상 recall/F1을 계산하지 않는다.
- 확정 라벨이 있으면 그 범위의 정확도·과병합/과분할·비용을 함께 비교한다. 라벨이 없으면 무결성 통과 설정들의 비용·반복 안정성과 agent 정성 평가를 바탕으로 “잠정 후보”를 제시하고, 최적값 확정은 보류한다.
- 가장 좋아 보이는 요소를 자동으로 조합하지 않는다. 최종 후보는 표의 E01~E12 중 이미 탐색한 설정 그대로 하나를 쓴다. 조합은 상호작용이 있는 별도 후속 실험이다.

#### 고정 검수 표본의 정확한 선정 알고리즘

입력 집합은 해당 영상 E00 r01의 `boundaries_final`에 있는 고유 경계 index다. 시작 0과 끝 sentence_count는 제외한다. 특정 예시 102/112/264/278 등 고정 검수 위치를 표본 풀에서 빼거나 더하지 않는다. 예시와 무작위형 표본은 별도 태그로 관리하고 중복 위치는 검수 레코드 하나에 태그만 합친다.

Python random이나 내장 hash() 대신 아래 SHA-256 순위를 사용해 OS·프로세스·Python 난수 구현 차이 없이 재현한다. seed는 모델 요청 seed가 아니다.

```python
from hashlib import sha256

def sample_boundaries(video_id, boundaries_final, sentence_count, seed=20261017):
    pool = sorted({i for i in boundaries_final if 0 < i < sentence_count})
    ranked = sorted(pool, key=lambda i: (
        sha256(f"{seed}:{video_id}:{i}".encode("utf-8")).hexdigest(), i))
    return sorted(ranked[:5])
```

선정된 목록뿐 아니라 source_run, source_artifact_sha256, pool, seed, algorithm=`sha256_rank_v1`, 선택된 index를 review_queue.json에 저장한다. 빈 집합이면 빈 표본을 기록하며 나머지 index를 임의로 보충하지 않는다. 기준 E00 r01 영상이 실패/부재하면 해당 고정 표본은 unavailable로 남기고 r02·T1·다른 실험에서 가져오지 않는다. 단, 고정 위치와 생성 가능한 경계 차이 검수는 계속한다.

각 index b의 검수용 전사는 고정된 원본 입력에서 `[max(0,b-12), b)`와 `[b,min(N,b+12))`를 붙인다. 추가 문맥을 보고 판정했다면 실제 범위를 기록한다. 이 검수 문맥은 모델 inference 설정을 바꾸지 않는다. final_only는 confirm 전에는 표본을 선정하거나 신규 모델 결과를 평가하지 않는다.

#### 후보 선정과 자동 단계 전환

1. search r01/r02가 모두 validated인 E01~E12만 후보 자격이 있다. 실패·미지원·한 회만 성공한 설정은 제외한다. E00은 대조군이며 후보로 중복 선정하지 않는다.
2. Cursor는 탐색 4개의 동일 검수 범위에서 과병합·과분할·반복 안정성·비용을 비교하고 한 후보를 선정한다. 사람 라벨이 있으면 우선 사용한다. 없으면 Cursor가 전사를 검토한 agent 평가와 근거를 남기며, Fw/iEM에만 맞춘 설정보다 H2/hGV에서도 전환과 예시 연결을 보존하는 후보를 우선한다. 판정 불명확한 항목은 unknown으로 기록한다.
3. 자동 실행기가 의미 평가를 수행할 수 없거나 품질 근거로 우열을 가리기 어려워도 사람 입력을 기다리며 멈추지 않는다. 이때 자격 있는 E01을 사전 정의된 기본 후보로 선택한다. E01도 자격이 없으면 남은 자격 후보 중 두 반복의 영상별 경계 Jaccard 평균이 높은 순, 평균 본 처리 호출 시간이 짧은 순, 실험 ID가 작은 순으로 결정한다. 이 선택은 품질 우승이 아니라 기술적 대체 후보임을 명시한다. 동률 계산은 반올림 전 값으로 한다.
4. 자격 후보가 없으면 selected_id=null과 근거를 저장하고 confirm의 후보 슬롯 2개를 skipped/no_eligible_candidate로 기록한다. confirm E00 2회는 계속 실행해 전체 입력 대조 결과를 확보한다.
5. selection.json에 selected_id, 선택 방식(human/agent/default/technical_fallback/none), 비교 근거·미검수 범위, search 결과 해시, 후보 실효 설정 해시, 입력 그룹, 확정 시각을 저장한다. confirm에서는 입력 그룹·출력 경로만 바꾸고 모델·프롬프트·하이퍼파라미터를 변경하지 않는다.
6. 선정 후 confirm 4회로 자동 진행한다. 추가 확인 4개의 결과가 나쁘다고 후보를 바꿔 다시 시도하지 않는다. 결과를 그대로 보고하고 최종 권고를 보류하거나 E00 유지를 권고한다. 재탐색은 새 campaign의 후속 작업으로 남긴다.

### 10. Cursor에 그대로 전달할 요청문

> tests/T1/validation_report.md의 ‘순차 반복 실험 명세’를 읽고, T1을 보존한 채 tests/T1_sweep에 설정 기반 실행기·평가기·중단 재개 기능을 구현해줘. 먼저 지정된 탐색용 4개 입력으로 E00~E12를 각각 2회씩 총 26회 순차 실행해줘. 탐색 결과만으로 기존 설정 중 잠정 후보 1개를 선정·고정한 다음, E00과 후보를 각각 2회씩 전체 8개 입력으로 총 4회 새로 실행해줘. 합계 30개 슬롯을 한 회차나 탐색 단계에서 멈추지 말고 끝까지 진행해줘. 사람 검수가 없어도 문서의 후보 선정·실패·미지원·시간 한도 규칙에 따라 이어가줘. 전체 결과와 탐색 4개/추가 확인 4개/전체 8개의 비교를 campaign의 summary.md에 정리해줘. 입력을 삭제하거나 T1을 덮어쓰거나 후보를 최종 결과에 맞춰 바꾸지 말아줘.
